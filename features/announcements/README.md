# Announcement student tags and supervisor sharing

## School audience selection

Create/edit defaults to **Whole department** (Department posts) or **General school audience** (General posts). The optional **Tagged students only** mode requires at least one tag and restricts school viewing to tagged students, their current department heads, the author and admins. Only involved students/heads (excluding the author) are notified; admins retain read access without an automatic notification. Visible to employers remains independent: checked adds the current supervisors of tagged students, unchecked adds no employers. Multiple students may share one supervisor; send one employer notification per post.

Apply `scripts/2026-10-31-targeted-announcement-audience.sql` once **after** the student-tags migration and before deploying both apps. It adds `tagged_students_only DEFAULT 0`, preserving old posts' broad school audience with no backfill. No environment/package changes. Edits validate the final tags/audience together; clearing the last tag of a targeted post fails unless switching to the usual audience. Audience edits reconcile notices: notify newly included recipients, remove excluded recipients' notices, and emit refresh events after commit. Targeted access overrides the broad category audience, including on dated calendar entries. Shared `targetedSchoolAccess` checks feed/count/pinned, direct links, calendar, inbox/count/mark-all and notification-open. Announcement history and notification reads are now private/no-store for all roles so current membership changes cannot serve an obsolete private audience from a server cache; category options remain cached.

The earlier description below of unchanged school visibility applies to posts using the **usual audience**; Tagged students only is the explicit exception.

Scope clarification: every regular department head is restricted to their current database department on both picker lookup and create/edit validation. Registrar heads are the explicit school-wide exception, like admins. All three can select multiple eligible students (up to 100). Regression coverage verifies cross-department rejection, Registrar/admin selection across departments, retained tags after a rejected edit and one supervisor notification when several selected students share that supervisor. This clarification needs no additional SQL migration.

Apply `scripts/2026-10-31-announcement-student-tags.sql` once **before** deploying the backend and matching frontend. It adds `announcements.employer_tagged_only` and the `announcement_student_tags` join table (composite primary key, student lookup index, cascading post/student foreign keys). Existing posts default to unrestricted employer scope, preserving their existing `visible_to_employers` checkbox behavior. No data backfill, packages or environment variables are needed. The existing public UUID and employer-visibility migrations must already be applied. Use the database containing these tables; their UUID columns must retain the matching utf8mb4_general_ci schema collation.

- Unchecked Visible to employers: no employer access or notification, whether students are tagged or not.
- Checked without tags: all employers, preserving the previous behavior.
- Checked with tags: only employers currently supervising a tagged student's ongoing, nondeleted internship. A tagged student without a supervisor does not grant employer access. Multiple tagged interns under the same supervisor produce one announcement notification for that employer. The usual General/Department school audience remains unchanged.

The authenticated `/announcements/tag-students?search=...` lookup is for admins/heads only: up to 30 name matches among nondeleted students with ongoing internships; regular heads use their current DB department, admin/Registrar heads can search all ongoing interns. JSON or multipart writes accept `tagged_student_ids` as an array or JSON array of up to 100 distinct UUIDs. The author-only existing update endpoint validates tags again, replaces them transactionally, and preserves them when omitted. Existing tags can be removed in the editor; newly selected students must still be eligible. Missing, malformed, finished or out-of-scope students roll back the post/tag mutation. Tag IDs and names are included in post read/edit data so the editor restores the saved selection.

`studentTags.js` supplies one SQL access predicate to feed (pinned/count/page), direct post lookup, notification list/count/mark-all and notification-open handling. Live `internship_records.employer_id`, status and deleted_at determine employer access. Former supervisors lose access; current supervisors can read the post. A later supervision change does not send a new notification automatically; announcement create/edit resolves notification recipients. Tag edits notify newly eligible, not already-notified employers and remove excluded employers' saved announcement notices. Checkbox-off removes employer notices. Post updates emit the existing `announcements_changed` event after commit so employer clients refresh.

The separate `employer_tagged_only` flag is intentional: deleting a tagged student's account/last join row must never make a restricted post visible to all employers. Employer feed/inbox/count routes bypass server route caches to recheck current supervision on each read; school-role cache behavior stays unchanged. Opening a notification still verifies recipient ownership and live post access. School category permissions, employer read-only access and the Calendar exclusion remain intact.

SQL order: existing public UUID + visibility migrations, then the October 31 migration, then backend, then frontend. No live database changes are performed by the implementation. The SQL is not meant to be rerun after its column already exists; inspect schema before a repeated deployment.

### Automatic tagged audience

Tags always force tagged_students_only=1 on create/edit using persisted tags, even when a stale client submits broad mode. Existing tagged posts require scripts/2026-10-31-tagged-announcements-default-private.sql after the earlier tag-table and targeted-audience migrations; it updates only the audience flag, with no schema change or new notifications. Live feed/direct/calendar/inbox guards enforce the restricted audience. Keep author/admin viewing, involved student/head notifications and optional current-supervisor sharing. Broad posts must have no tags.


### Announcement mutation reliability

Announcement mutations: edit recipient reconciliation compares live eligible users before and after the write under the announcement lock, independently of existing alerts. Ordinary edits must not recreate dismissed notifications; only newly eligible recipients are notified. Remove out-of-audience UUID and legacy numeric-link alerts. Pin accepts only numeric/string 0 or 1; admin may pin any existing post, heads must pass fresh DB department/Registrar and targeted viewing checks. Pin commits before silent announcements_changed events; socket failures do not report the saved pin as failed. Existing client listeners refresh announcement, notification and calendar queries. No new SQL/schema/env settings are needed for these mutation fixes; earlier tagging migrations remain required.
