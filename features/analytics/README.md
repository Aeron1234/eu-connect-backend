# Company analytics and Registrar overview

`GET /api/v1/analytics/companies`: admin or non-Registrar department head only. `GET /api/v1/registrar/dashboard`: current Registrar head only. Both retain the `/eu-connect/api` compatibility mount. Every read verifies the signed role and resolves heads' current database department via `dept_heads_background_info`/`departments`; token department claims never grant scope. Missing departments, student/employer access, Registrar popularity access and ordinary-head Registrar access fail closed. Responses are private/no-store. A repeatable-read transaction supplies all sections of a single snapshot; failures roll back and release rather than returning partial/placeholder totals.

## Company popularity definition

- Source: `internship_records` with status **ongoing** or **finished**, nondeleted placement and nondeleted linked user. Pending/rejected are not confirmed placements; applications/postings are never counts. Academic membership comes from each student's latest `student_academic_info` row. Heads see only that department, including its authorized history; admins can filter any department.
- Company identity: trim/collapse whitespace and lowercase the name. Same-name branches combine, consistent with the existing company directory's name-based identity. Different aliases remain separate. There is no authoritative company master ID; this does not claim legal-entity matching. Names are normalized for reporting, not rewritten in the database.
- Popularity: distinct **student/company pairs** within the selected filters. Repeat records at the same company count once. Distinct students across all companies may be smaller. Ongoing has precedence over finished when both occur for a pair in the selected records, so ongoing + finished equals each company's student count and aggregate status totals equal pair totals.
- Descending competition ranks, alphabetical tie ordering, all ties in most/least lists. Least popular includes only positive counts. Distribution percentages use pair totals, not global distinct students. Chart comparison shows top ten; distribution shows top five plus Others; table/export includes all companies.
- Zero universe: company names from the same department/course's accessible confirmed history plus the existing manual alumni company directory, across all dates. Alumni entries establish known company names only because they lack reliable linked student IDs; they never add popularity counts. A zero means no matching confirmed placements in this selected period, not an unfilled vacancy or an exhaustive list of all companies worldwide. Zero rows never enter least-popular ranking.

## Filters and time

Admin: optional `departmentId`, dependent `courseId`, `academicYear`, `term`, `from`, `to`. Head: course/year/term/dates; department injection is rejected and the course must belong to the head's current department. Valid terms are `1st`, `2nd`, `summer`. Dates are valid inclusive YYYY-MM-DD **placement start dates**, not interval overlap, application/submission date or attendance. Year/term/date filters intersect. Unfiltered means all history; undated records remain in all-time counts but cannot satisfy a year/date constraint. Explicit terms can still include undated records if no date/year constraint exists. Unnamed-company records are excluded and counted in the disclosure.

Academic-year derivation matches the existing `internship_records_with_ay` CASE exactly: first semester uses its start year; second-semester December uses its year, January-April use prior year; summer uses prior year; null semester July-December uses its year; remaining cases use prior year. Derivation is reused semantically in a tested pure function so no view/definer change is required. Department/course means **current/latest membership**, not a historical snapshot (the schema does not record one per placement).

Trends count distinct pairs within each actual recorded start month. A pair recurring in different months appears in each relevant point, so monthly points are not additive to an all-period distinct total. Months with no recorded starts are omitted. Cards, detailed report, rankings and distribution come from the same model; no independently filtered counts can drift.

## Registrar permission audit and metrics

Existing Registrar features already authorize global SIPP Annex C drafts/submitted reports and Annex D confirmed placements; `isRegistrarHeadOrAdmin` verifies that access in the existing report handlers. The new dashboard uses only these data sources. It does **not** add private DTR/evaluation/document review, student-account administration, approval/correction queues, missing-document inference or company popularity. No new permission grant is made.

`academicYear` is the sole Registrar filter; omitted/reset uses the existing SIPP current-academic-year helper. There is no all-years Annex D dashboard mode because its existing report endpoint defaults to a single year. Counts: saved Annex C total, draft, submitted; distinct confirmed Annex D students; supplemental confirmed record count. Department/course coverage uses distinct students in that Annex D population. Source follows existing report rules: nondeleted ongoing/finished records with a latest academic/course and profile. Retained soft-deleted accounts may remain in this historical Annex D population, as in the official report; company analytics separately excludes deleted accounts. Submission trend uses real `submitted_at`; recent ten reports use saved update/create timestamps. No invented verified/returned states.

Dashboard cards navigate to existing SIPP pages with `tab`, `year`, `status` preserved; those are validated on the page and seed existing Annex C/Annex D queries. Draft links open the report list, not a fabricated verification task. Existing report preview/PDF export remains there. Registrar now has Dashboard navigation at `/department_head`; its previous redirect directly to SIPP is removed. Non-Registrar dashboard behavior remains, with a company analytics link; Registrar has none.

## Database / deployment

Run `scripts/2026-10-31-company-analytics.sql` first to verify existing tables/types/indexes, deploy backend second, frontend third. It is read-only/repeatable. No schema, relationships, data backfill, environment or dependency changes are required. Existing placement status/date and user/academic lookup indexes are suitable; do not import a historical database dump or alter the year view. Analytics does not query the live database during implementation/testing. Aggregation reads scoped confirmed history in one request; at substantially larger historical volumes, profile the data before considering materialized aggregates.

Frontend uses existing DashboardStats (one phone column), ChartContainer/Recharts with responsive tap/hover tooltips, shadcn DropdownFilter, loading/error patterns, table overflow containers and react-to-print. CSV and browser Print / Save PDF export the full filtered aggregate and zero lists, not a single table page; CSV guards formula cells. No individual students' private data is exported. CSV/print supplement existing official Annex exports; ordinary heads are not granted SIPP export access.

Regression: `node --test tests/company-analytics.test.js` (in-memory SQLite fixture with MySQL date-function adapter; loopback mounted-route checks). Covers roles, latest department transfer, distinct pair/status totals, zero handling, inclusive bounds/terms/years, official Registrar population and rollback. Real MySQL repeatable-read locking is not simulated by SQLite.

Implementation validation: 18 backend tests passed across this feature and existing `reports-cache` regressions. The paired frontend passed its production build, targeted lint and 20 dashboard/help/navigation tests. Isolated browser fixtures verified both screens at 320×721, 768×900 and 1440×900, touch tooltip bounds, local table scrolling, full CSV/print exports and Registrar navigation restrictions. These fixture checks do not validate production data, live MySQL concurrency or a deployment; no live database was read or modified.
